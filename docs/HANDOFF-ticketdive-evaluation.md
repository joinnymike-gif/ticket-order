## 2. 网络访问：新会话开工前必须先验证

### 2.1 上一会话观测到的拦截

代理端点 `$HTTPS_PROXY/__agentproxy/status` 记录的全部为策略拒绝（gateway 对 CONNECT 返回 403）：

```
ticketdive.com:443          connect_rejected
www.ticketdive.com:443      connect_rejected
lp.ticketdive.com:443       connect_rejected
ticketdive.zendesk.com:443  connect_rejected
```

curl 与 WebFetch 两条路径均被挡，WebFetch 直接返回 `EGRESS_BLOCKED`。

### 2.2 该环境的策略形态

对照探测结果表明这是**"默认全禁、仅放行 GitHub + 包管理源"**的严格白名单，而非"全通但禁了个别域名"：

| 主机 | 结果 |
|---|---|
| example.com | 被拒 |
| www.google.com | 被拒 |
| github.com | 通 |
| registry.npmjs.org | 通 |

### 2.3 为什么"已放行"却仍被拦

网络策略在**容器创建时快照**。白名单的修改晚于旧容器启动时间，旧容器仍在用旧策略 —— 所以必须**新开会话**（新容器）才会生效。

### 2.4 需要放行的主机（只加裸域名不够）

站点内容分散在三个主机上：

- `ticketdive.com` — 用户侧主站（含活动页、登录、下单）
- `www.ticketdive.com` — 同上
- `lp.ticketdive.com` — **主办方侧落地页**，产品定位与功能清单在这里
- `ticketdive.zendesk.com` — **帮助中心**，现有流程的痛点与边界条件在这里

### 2.5 新会话第一件事：跑这条命令确认

```bash
for h in ticketdive.com www.ticketdive.com lp.ticketdive.com ticketdive.zendesk.com; do
  printf "%-28s " "$h"
  curl -sS -o /dev/null -w "http_code=%{http_code}\n" --max-time 15 "https://$h/" 2>&1 | tail -1
done
```

拿到 `200`/`3xx` 才算通。仍是 `000` + `CONNECT tunnel failed, response 403`，说明白名单没保存成功或环境没换 —— **此时不要绕行**（缓存镜像、第三方抓取代理、文本化代理都属绕行，代理规则明确禁止），直接向用户报告被阻主机。

参考：环境与网络策略配置见 https://code.claude.com/docs/en/claude-code-on-the-web

## 3. 已知的 TicketDive 公开信息

来自公开搜索（**未经站点实地核实，新会话须逐条验证**）：

- 日本的活动票务平台，覆盖乐队、偶像、演剧、お笑い、体育、舞蹈、讲座等品类
- 同时承担**申込（报名）**与**售票**两类流程
- 主办方端宣称**免手续费**，以此区别于大手票务商
- 支付方式：信用卡 / 便利店支付 / PayPay
- 出票形态：纯电子票 / 纯纸质票 / 由购票者选择
- 受众地域：日本为主，其次台湾、香港
- 流量量级：月访问约 40 万，平均停留 12 分钟以上（停留偏长，值得在评估中追问是"内容黏性"还是"流程卡顿"）

已知可用作样本的活动页 URL 形态 `ticketdive.com/event/<id>`，公开可见的样本 id：
`LiveGymEx20260720`、`260714higashinihon`、`DqTZby4GfXbs98COiajM`。

## 4. 评估框架

### 4.1 采集清单（按用户旅程顺序抓）

1. 首页 `/`
2. 活动详情页 `/event/<id>` —— 至少取 3 个不同品类做对比
3. 登录 / 注册 `/signin`
4. 选票 / 申込表单（抽選 与 先着 两种模式都要拿到）
5. 结算与支付分支（信用卡 / 便利店 / PayPay 各走一遍界面）
6. 完成页 与 我的票夹 / 电子票展示
7. 主办方侧 `lp.ticketdive.com`（功能清单、定价、后台截图）
8. 帮助中心 `ticketdive.zendesk.com` —— 重点检索「変更」「キャンセル」「支払い」「入場」「抽選」，用户实际痛点集中在这里

> 未登录/未付款状态下能看到的界面有限。把"哪些环节因未登录而无法观测"如实记录下来，不要靠猜补全。

### 4.2 评估维度

**A. 转化漏斗与信息架构**
从活动页到支付完成需要几步、几次跳转、几次登录中断；有无游客下单；返回/刷新是否丢状态。

**B. 报名（申込）表单**
字段数量与必填比例；同行者信息如何采集；抽選 vs 先着 的表单差异；实名/年龄/会员校验；错误提示时机（实时校验还是提交后整页报错）。

**C. 选票与库存并发**
座席图 / 整理番号的选择方式；库存锁定（hold）时长与是否有倒计时提示；开票瞬间高并发下的排队机制；超卖与并发扣减的处理痕迹。

**D. 支付**
三种方式的分支设计；**便利店支付的"待付款"状态机**是重点 —— 付款期限、期限内库存是否占用、超时释放逻辑、提醒方式；支付失败与重试路径。

**E. 出票与入场核销**
电子票二维码的生成与刷新策略（静态码 vs 动态码）；防转售/防截图措施；纸质票配送流程；入场分流与离线核销兜底。

**F. 移动端与性能**
日本移动端占比高，以移动优先视角评估：首屏时间、活动页图片体积、表单在小屏下的可用性、支付页的键盘与输入类型。

**G. 多语言**
受众含台湾、香港 —— 是否有繁体中文；日期/时间/货币/姓名顺序的本地化；未本地化时台港用户的实际卡点。

**H. 合规与无障碍**
特定商取引法表记、个人情报保护方针、抽選公平性说明的可见性；键盘可达性、对比度、表单 label 与 aria 标注。

**I. 主办方后台**
建活动的流程复杂度、售卖数据可见性、退改票操作成本 —— 这决定平台的供给侧留存。

### 4.3 产出物

评估完成后应交付：

1. **现状记录** —— 每个环节的实测截图/文字，明确标注哪些环节未能观测及原因
2. **问题清单** —— 按「影响面 × 修复成本」排序，每条附具体证据（页面 + 复现步骤），不写无证据的主观判断
3. **改版方案** —— 针对高优先级问题给出具体设计，涉及库存并发与支付状态机的部分要写清状态流转
4. **取舍说明** —— 明确哪些建议受限于"仅能观测前端"而无法确认，需要产品方确认后再定
